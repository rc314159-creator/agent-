# 知识库维护规则（Auto-Picture 项目专属）

> 全局通用 kb 规则见 `~/.claude/skills/kb/SKILL.md`，本文档是 Auto-Picture 项目专属补充和落地约定。

## 一、三层信任硬规则（绝对不能违反）

| 层 | 角色 | 权威度 |
|---|---|---|
| **docs/** | 唯一真相源（意图 + 设计） | **最高** |
| **代码** | docs 的实现 | 仅"现状" |
| **外部产物**（DB / 飞书 / GitHub PR） | docs 的镜像 | 落后正常 |

冲突解决方向（**严禁反向**）：
- 代码与 docs 冲突 → 改代码朝向 docs
- 用户 intent 与 docs 冲突 → 改 docs 朝向 intent

## 二、什么时候必须改 docs

### 2.1 触发条件清单

| 触发 | 必改文件 |
|------|---------|
| 实现一个**新功能** | `docs/功能模块/<功能名>.md` 新建 + `docs/INDEX.md` 加索引 |
| 改了**架构**（端口/进程/数据流） | `docs/架构设计/系统架构.md` 覆盖式更新 |
| 修了**bug** | `docs/开发计划/YYYY.MM.DD/<topic>.md` 追加，附上修复方案 |
| 改了**任意可调参数**（阈值/默认值/Provider） | 对应 `docs/功能模块/<功能>.md` 覆盖式更新表格 |
| 起一个**迭代** R\* | `docs/开发计划/YYYY.MM.DD/r<N>-<topic>.md` 新建 |
| 完成一个迭代 | 同上 frontmatter 改 `execution_status: 已完成` |
| 发现**已知缺陷**但暂不修 | `docs/_GAP.md` B 节加条目，标 ID + 优先级 + 触发条件 |
| 发现**docs 跟代码漂移** | `docs/_GAP.md` A 节加条目 |

### 2.2 反例（**不要**写到 docs）

- ❌ 临时调试日志（写到 commit message 就够）
- ❌ 个人记笔记（去 memory）
- ❌ 复制粘贴代码大段（spec 是设计意图不是代码副本）
- ❌ "TODO: 想到再补" 字样（要么写完整，要么不写）

## 三、文件归属决策表（IS-A 链推理）

按"它**是什么**而不是它像什么"分类（kb skill 五律之"本质特征"）。

| 文档实质 | 归类 |
|---------|------|
| "这个项目是干啥的" | `项目概述/项目总览.md` |
| "怎么装怎么跑" | `项目概述/运行环境.md` |
| "跨模块的整体架构 / 数据流" | `架构设计/<topic>.md` |
| "单个功能模块的实现细节" | `功能模块/<功能名>.md` |
| "某天做了哪些事 / 这个迭代要做什么" | `开发计划/YYYY.MM.DD/<topic>.md` |
| "怎么验证某功能跑得对" | `自动化测试/<功能>.md`（AI 详细版）+ 引用到 `自动化测试/_人类版_验收手册.md`（精简） |
| "已废弃但不删的资料" | `历史归档/<version>/` |
| "本项目通用规则" | `规范/<规则名>.md`（本文档所在目录） |
| "知识库与代码的已知差距 / 待办" | `_GAP.md` |

### 决策反例
- ❌ R12 重连机制写到 `开发计划/2026.05.20/r12-*.md`，但**没**同步到 `功能模块/ASR容错.md` → 漂移
- ❌ 一份功能 spec 同时讲架构和测试 → 拆成 `功能模块/X.md` + `自动化测试/X.md`
- ❌ "声纹算法" 写到 `架构设计/` → 那是单模块细节，应在 `功能模块/`

## 四、文件命名规则

| 维度 | 规则 |
|------|------|
| 语言 | 全中文（除非术语必须英文，如 `R12-llmmelon-default.md`） |
| 大小 | 单文件 ≤ 500 行，超了拆 |
| 后缀 | `.md` 唯一 |
| 日期目录 | `YYYY.MM.DD` 格式（不要 `2026-5-20`）|
| 迭代命名 | `r<N>-<kebab-case-topic>.md` |

## 五、Frontmatter 强制字段

所有 spec 类文件（项目概述/架构设计/功能模块/规范）必须：

```yaml
---
title: <标题>
description: <一句话描述，<200 字符，给 INDEX 和 Agent 用>
status: 已批准 | 起草中 | 已废弃
created: YYYY-MM-DD
updated: YYYY-MM-DD
update_reason: <这次为什么改>
related:
  - docs/xxx/yyy.md
---
```

开发计划额外加：
```yaml
execution_status: 未开始 | 执行中 | 已完成
```

## 六、INDEX 维护

`docs/INDEX.md` 是**唯一入口**，规则：
- 任何新增 spec 文件 → INDEX 必须加一行
- 任何被废弃文件 → INDEX 标 ~~strikethrough~~ 不删除
- INDEX 自身 ≤ 200 行（超了把详细描述移走，只留索引）

## 七、提交流程

每次 commit 前自检：
```
1. 我改了 web/src/lib/xxx.ts → 对应 docs/功能模块/xxx.md 改了吗？
2. 改了 web/src/app/api/xxx/route.ts → docs/自动化测试/<相关>.md 的 API 端点表更新了吗？
3. 这是新功能？docs/INDEX.md §二某节加索引了吗？
4. 这是迭代收尾？docs/开发计划/YYYY.MM.DD/r<N>-*.md 写了吗？execution_status 改了吗？
5. 改完跑：cd web && npx tsc --noEmit + 必要的 curl 验证
```

## 八、健康度审计触发

每 10 个 commits 或每周（取先到）跑一次 kb audit：

```
□ INDEX 覆盖：所有 .md 都被 INDEX.md 或某文档引用？
□ frontmatter 合规：所有 spec 都有 status / updated / update_reason？
□ 死链：所有内部链接可达？
□ 新鲜度：updated 距今 > 90 天且 status=已批准 → 是否还准确？
□ MECE：每个目录子项分类维度统一？
□ 命名一致：同目录命名风格统一？
□ 粒度对齐：同目录文件行数差异 < 5x？
□ 孤儿率：未被 INDEX/其他文件引用的 .md 数？
□ docs vs 代码：spec 描述的端点/字段/参数和代码一致？
□ _GAP.md 是否有未跟进的 B.* 条目？
```

不过 → 标 audit FAIL，加任务到下一迭代。

## 九、与 kb skill 的关系

- 本文档是 Auto-Picture 项目专属约定
- 通用规则在 `~/.claude/skills/kb/SKILL.md`（五条分类律、五个反模式、organize 6 步等）
- 两者不冲突时以**本文档**为准（项目本地优先）
- 跑 `/kb audit` 时引用本文档第八节的项目专属审计清单

## 十、Agent 工作时的具体约束

每个 Agent 任务（无论 worker / kb-keeper / critic / leader）：

1. **首先读** `docs/INDEX.md` + 任务相关的 `docs/功能模块/*.md` 和 `docs/架构设计/*.md`
2. **改代码前** 先验证 docs 与代码当前一致，不一致 → 先改 docs 朝向意图，再改代码
3. **commit 前** 自检本文档第七节清单
4. **遇到边界情况** 优先 `_GAP.md` 加条目而不是擅自重构

违反上述任一条 = audit FAIL，下次必修。
